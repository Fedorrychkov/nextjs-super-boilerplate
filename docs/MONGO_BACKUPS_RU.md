# Бэкапы MongoDB (локальная база в контейнере)

Реализация раздела 5 из `INFRASTRUCTURE_TODO_RU.md`. Работает **только для локальной Mongo** (`mongo_enabled: true` в деплое): если база ремоутная — контейнера нет, бэкапить нечего, используйте бэкапы провайдера кластера.

## Как это работает

- **`scripts/backup-mongo.sh`** — `mongodump --archive --gzip` в файл `~/db-backups/mongo_<env>_<дата>.archive.gz`.
- Дампы лежат в **`~/db-backups`** — рядом с `~/app`, но снаружи: blue/green-свопы (`app` → `app.bak`, `app_new` → `app`) их не трогают.
- **Расписание — системный cron** на сервере, ставится и снимается деплой-воркфлоу. Сознательно не воркер-джоба: бэкапы не должны зависеть от Redis/BullMQ — страховка обязана быть тупой и автономной.
- **Ротация**: после успешного дампа хранится N последних (`mongo_backup_retention`, дефолт 14). Ошибочные/пустые дампы удаляются сразу (проверка `gzip -t` + размер).
- Лок от наложения запусков, гард по свободному диску (дефолт 500MB), самообрезающийся `backup.log`.

## Включение через деплой

Автоматика: `mongo_enabled: true` → бэкапы включаются сами (`mongo_backup_enabled` по дефолту `true`). Выключил Mongo на редеплое → cron снимается, ничего не ломается, накопленные дампы остаются.

```yaml
with:
  mongo_enabled: true
  # опционально:
  mongo_backup_enabled: true      # false — выключить бэкапы, не выключая mongo
  mongo_backup_cron: '30 3 * * *' # серверное время; выбирай ночное окно
  mongo_backup_retention: 14      # сколько дампов хранить
```

Крон-строка помечена маркером `# bp-mongo-backup` и обновляется идемпотентно — смена частоты/ретенции применяется следующим деплоем.

### Формат расписания (crontab)

Пять полей: `минута час день-месяца месяц день-недели`. Звёздочка — «любое значение». **Время серверное** — на типичном VPS это UTC (03:30 UTC = 06:30 МСК); проверить: `timedatectl` на сервере.

| `mongo_backup_cron` | Когда запускается |
|---|---|
| `30 3 * * *` | каждый день в 03:30 (дефолт) |
| `0 2 * * *` | каждый день в 02:00 |
| `0 */6 * * *` | каждые 6 часов (00:00, 06:00, 12:00, 18:00) |
| `0 2,14 * * *` | дважды в день — в 02:00 и 14:00 |
| `0 4 * * 0` | раз в неделю, воскресенье 04:00 |
| `0 4 1 * *` | раз в месяц, 1-го числа в 04:00 |
| `15 3 * * 1-5` | по будням в 03:15 |

Подбирая частоту, помни про связку с `mongo_backup_retention`: ретенция считается в дампах, а не в днях. Дефолт 14 при ежедневном запуске — две недели истории; при `*/6` те же 14 дампов — всего ~3.5 дня. Увеличил частоту — увеличь и ретенцию (и посматривай на диск: гард в скрипте пропустит бэкап при <500MB свободного).

## Нагрузка на CPU/RAM (важно при динамических лимитах памяти)

`mongodump` запускается **не** через `docker exec` в mongo-контейнер, а в отдельном одноразовом контейнере (тот же образ, что у работающей mongo — версии тулов совпадают всегда), который делит с mongo только сетевой неймспейс. Почему это важно:

- `docker exec` выполнялся бы **внутри cgroup mongo** — дамп ел бы бюджет памяти, выданный базе через `memory-limits.sh`, и под нагрузкой мог бы спровоцировать OOM-kill mongod.
- У одноразового контейнера свои жёсткие капы: `--memory 256m --cpus 0.5` (дефолты; `MONGO_BACKUP_MEM_LIMIT` / `MONGO_BACKUP_CPUS`). Gzip-сжатие тоже происходит внутри него.
- В бюджет `memory-limits.sh` дамп-контейнер **не входит** сознательно: он живёт минуты и в ночное окно — выделять ему постоянную долю значило бы отнимать её у api/mongo круглосуточно. Капы вместо доли.
- На mongod сам дамп даёт умеренную читающую нагрузку; на маленьком сервере (1 vCPU) `--cpus 0.5` не даёт задавить приложение. WiredTiger-кэш mongo не раздувается от mongodump.

## Восстановление

```sh
ls ~/db-backups/                          # выбрать дамп
ENV_FILE=.env.prod ~/app/scripts/restore-mongo.sh ~/db-backups/mongo_prod_20260717_033001.archive.gz
```

Скрипт спросит подтверждение (`FORCE=1` — для скриптованного восстановления). **`--drop`: существующие коллекции заменяются содержимым дампа.** Порядок при серьёзной аварии:

1. Остановить запись: `docker stop api-service worker-service` (nginx отдаст 502 — честнее, чем писать в битую базу).
2. Прогнать restore, проверить ключевые коллекции через `mongosh`.
3. Поднять api обратно: деплой или `docker start api-service worker-service`.

## Скачать бэкап на свою машину

С ноута (не с сервера). Подставь юзера/хост своего сервера:

```sh
# последний дамп одной командой
scp "user@server:~/db-backups/$(ssh user@server 'ls -1t ~/db-backups/mongo_*.archive.gz | head -1 | xargs basename')" ~/Downloads/

# конкретный файл
scp user@server:~/db-backups/mongo_prod_20260717_033001.archive.gz ~/Downloads/

# все дампы разом (докачивает только новые — удобно гонять периодически)
rsync -avz --progress user@server:~/db-backups/ ~/backups/myproject/
```

С таким локальным дампом можно и поднять базу у себя: `MONGO_CONTAINER=<локальный mongo-контейнер> ENV_FILE=.env.local ./scripts/restore-mongo.sh ~/Downloads/mongo_prod_....archive.gz` — удобно отлаживать прод-баги на реальных данных.

## Ручной запуск / проверка

```sh
ENV_FILE=.env.prod API_ENV=prod ~/app/scripts/backup-mongo.sh   # разовый бэкап
tail -50 ~/db-backups/backup.log                                # лог кронов
crontab -l | grep bp-mongo-backup                               # расписание стоит?
```

## Офсайт (следующий шаг, вручную)

Дампы на том же диске защищают от «уронил базу», но не от потери сервера. Когда дойдут руки — добавь в конец `backup-mongo.sh` выгрузку в object storage (`rclone copy` / `mc cp` в S3-совместимый бакет). Ретенция в бакете — отдельно, средствами стораджа (lifecycle rules).
