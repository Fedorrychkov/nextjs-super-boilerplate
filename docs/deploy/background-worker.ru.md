# Фоновый воркер и кроны — архитектура и использование

Бойлерплейт включает опциональный фоновый воркер — отдельный headless-контейнер для периодических задач (кроны, свипы, коллекторы, очереди). Из коробки он выключен и не влияет на API; включается флагом на деплое. Архитектура портирована из боевых проектов вместе с граблями, на которых там уже наступили.

## Главная идея

Крон здесь — это **не расписание в самом планировщике**, а тонкий «тик», который дёргает идемпотентную функцию. Расписание живи́т в БД:

- у периодически обрабатываемой сущности есть поле `nextRunAt` (+ `intervalSec`, `enabled`);
- «тик» раз в N секунд выбирает всё, что уже пора (`nextRunAt <= now`), обрабатывает пачку и двигает `nextRunAt` вперёд (**в `finally`** — иначе упавшая запись застрянет и будет молотиться каждый тик);
- сам механизм запуска тика — сменный: BullMQ-воркер, HTTP-роут с `CRON_SECRET` под внешний планировщик, либо one-shot CLI под системный cron. Все зовут одну и ту же функцию.

Логика расписания не завязана на BullMQ: источник правды — база, раннер можно заменить чем угодно.

## Что уже готово в бойлерплейте

| Часть | Файл |
| --- | --- |
| Generic-планировщик (BullMQ, реестр джоб) | `lib/services/worker-scheduler.ts` |

| Отдельное Redis-подключение для BullMQ | `lib/redis.ts` → `createBullMqConnection()` |
| Контейнер воркера | `docker-compose.local.yml` → сервис `worker` |

| npm-скрипты | `worker`, `worker:local`, `worker:stage`, `worker:prod` |

### Как добавить свою джобу

В `scripts/worker.ts` добавь элемент в реестр `jobs`:

```ts
{
  name: 'my-sweep',                       // уникальное имя = BullMQ jobId
  intervalMs: 60_000,
  enabled: isOn(process.env.MY_SWEEP, true), // гейт через env-флаг
  run: async () => processDueThings(),    // идемпотентная функция, batch-лимит внутри
}
```

`run` должна: выбрать due-записи из БД → обработать пачку (лимит!) → подвинуть `nextRunAt` в `finally`. Планировщик сам чистит stale-расписания при смене `intervalMs` или удалении джобы.

### Как включить воркер на окружении

1. Локально: `pnpm run worker:local` (нужен `REDIS_URL`).
2. Compose: сервис `worker` поднимается тем же образом, что `core-api`, но с командой `worker:<env>`.
3. Деплой: в вызове reusable-workflow поставить `worker_enabled: true` (требует `redis_enabled: true`). Лимит памяти — авто-слайс от `server_memory_mb` или явный `worker_mem_limit`.

Без Redis воркер деградирует в no-op с warning — контейнер можно держать включённым в конфиге, ничего не упадёт.

## Свойства, которые нельзя терять при доработке

- **`advanceSchedule` в `finally`.** `nextRunAt` двигается даже если обработка упала.
- **Батч-лимит.** Обрабатывается пачка, не всё сразу: защита от serverless-таймаутов и эффекта «толпы».
- **Один инстанс воркера.** `core-api` масштабируется свободно; воркер — singleton, иначе двойные тики.
- **Защита от ложных срабатываний при своей аварии.** Если в батче аномально велика доля сетевых ошибок — проблема у воркера (сеть/DNS), а не у обрабатываемых сущностей; переходы состояний стоит пропустить (см. `shouldTreatBatchAsProbeInfraOutage` в quickping).

## Отдельный серверный инстанс

Воркер — **отдельный контейнер**, не часть API:

- тот же образ, что `core-api`, другая команда запуска — `pnpm run worker:$API_ENV`;
- **не слушает HTTP** → Docker-`HEALTHCHECK` на `localhost:3000` принудительно отключён (`healthcheck: disable: true`), иначе контейнер вечно `unhealthy`;
- `restart: unless-stopped`, отдельные `WORKER_MEM_LIMIT` / `WORKER_NODE_OPTIONS`;
- на деплое force-recreate (stateless singleton, короткий рестарт допустим), без blue/green.

Смысл разделения: фоновая работа не конкурирует за ресурсы и рестарты с веб-инстансом, масштабируется и падает независимо.

## Грабли, на которых уже наступили (учтены в коде)

1. **Redis пухнет бесконечно.** BullMQ по умолчанию хранит completed/failed jobs **навсегда**. С тиком раз в минуту это ~840MB за 20 часов и OOM-kill хоста. Лечится `defaultJobOptions.removeOnComplete/removeOnFail` (в `worker-scheduler.ts`: ~100 последних на час; фейлы — дольше).

2. **Дублирующиеся тики при смене интервала.** Repeatable job ключуется парой `(name + every)`. Смена интервала через env оставила бы старое расписание жить рядом с новым → двойные тики. Поэтому на старте воркер вычищает stale repeatable jobs (в т.ч. от удалённых/переименованных джоб).

3. **Два разных Redis-клиента.** BullMQ требует `maxRetriesPerRequest: null` (блокирующие команды), обычный клиент приложения — `1` (fail-fast кэш). Один инстанс переиспользовать нельзя: в `lib/redis.ts` две фабрики — `createBullMqConnection()` для воркера и `redisClient` для приложения.

4. **Redis-эвикция ломает очередь.** В проде Redis должен работать с `--maxmemory-policy noeviction` (уже так в compose): если BullMQ-ключи вытесняются, очередь повреждается.

5. **`concurrency: 1`.** Джобы обрабатываются по одной — параллельные батчи умножали бы нагрузку на Mongo и внешние вызовы.

6. **bullmq не попадает в API-бандл.** В `worker-scheduler.ts` модуль импортируется лениво через widened-спецификатор (`const BULLMQ_MODULE: string = 'bullmq'`), чтобы тайпчекер/бандлер Next не тянули его в веб-сборку.

## Альтернативные раннеры (если BullMQ/Redis не подходит)

Та же идемпотентная функция, другой триггер:

- **HTTP endpoint** — `GET /api/cron/<job>` с `Authorization: Bearer <CRON_SECRET>`; внешний планировщик (Vercel Cron, GitHub Actions, crontab) дёргает URL. Для serverless: `maxDuration` + батч-лимит на вызов. Пример: `src/app/api/cron/uptime/route.ts` в quickping.
- **One-shot CLI** — скрипт «один прогон и выход» под системный `cron`/`systemd timer`; нужен только Mongo. Пример: `scripts/uptime-tick-once.ts` в quickping.

## Референсы в родственных проектах

- **quickping** — эталон полной схемы: `lib/services/uptime-probe.service.ts` (ядро с `nextRunAt`), три раннера, инфра-защита от ложных инцидентов.
- **ticker-scanner** — воркер с WS-коллекторами + биллинг-крон, env-гейты отдельных джоб, CI-обвязка `worker_enabled`/`worker_mem_limit`.
- **платформа с кронами обслуживания** — несколько repeatable-джоб в одной очереди с разными интервалами.
