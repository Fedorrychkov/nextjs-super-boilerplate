# Журнал решений

Почему сделано именно так. Дизайн-доки в `docs/` описывают, **как** устроено; здесь — **почему** и
**почему не иначе**, с датой. Читается, когда хочется что-то переделать: сначала посмотри, не
отвергалось ли это уже и по какой причине.

**Задним числом не переписываем.** Решение изменилось — добавляется новая запись с датой и ссылкой
на прежнюю, старая остаётся как была. Иначе журнал перестаёт быть свидетельством. **Нумерацию не
менять**: на `§N` ссылаются комментарии в коде и другие документы.

## Форма новой записи

```
## N. Короткое название — DD.MM.YYYY

**Контекст.** Что происходило и почему понадобилось решение.
**Решение.** Что выбрали.
**Почему не иначе.** Какие варианты отвергли и чем они плохи. Отрицательный результат
записывается здесь же — он закрывает вопрос и экономит второй заход.
**Последствия.** Что теперь нельзя или станет дороже.
**Что сделать при выкатке.** Миграции, индексы, секреты, порядок, что необратимо. Пропускается,
если ничего не требуется. Агент не деплоит — это единственный канал к владельцу.
```

## 1. Контракт агента — один файл, адаптеры тонкие, размер под гейтом — 05.09.2026

**Контекст.** Несколько боевых проектов независимо пришли к одной схеме: `AGENTS.md` — единственный источник правил, `CLAUDE.md` —
адаптер на несколько строк с `@AGENTS.md`. В одном из них правила перенесли в `AGENTS.md` и тем же
движением переполнили файл: Codex обрезает инструкции после 32 КБ **молча**, часть правил просто
перестала существовать для агента.

**Решение.** `AGENTS.md` (EN, канонический) и `AGENTS_RU.md` держатся синхронно и под 28 КБ,
`@file`-импорты внутри контракта запрещены, `CLAUDE.md` не больше 4 КБ и только про рантайм.
Проверяет `scripts/check-agent-contract.mjs` через `pnpm gates` в CI.

**Почему не иначе.** Раскладывать правила по `.cursor/rules`, `.claude/skills` и `CLAUDE.md`
означает, что одно правило связывает один инструмент и молча не связывает другой. Размер глазами
не виден — поэтому проверка машинная, с запасом 4 КБ до потолка.

**Последствия.** Справочная часть (стек, структура) остаётся в `AGENTS.md`, пока помещается; при
росте её выносят в `docs/STACK_*.md`, а не ужимают правила.

## 2. Гейт внешних операций в Claude Code — по строке команды, fail-closed — 05.09.2026

**Контекст.** `prod-deploy.yml` триггерится на push в `main`: для агента `git push` — это
потенциальная выкатка в прод, а не «коммит уехал». Правило «не пушить» в тексте контракта
держится на дисциплине модели; гейт `PreToolUse` держится на коде.

**Решение.** `.claude/settings.json` вешает `scripts/guard-external.sh` на Bash. Скрипт ловит
**запуск** `git push` в любой форме (`cd x && git push`, `git -C . push`), pnpm-скрипты с суффиксом
`:prod` / `:stage`, команды с именем файла `.env.prod` / `.env.stage`, запуск `restore-mongo.sh` и
`mongorestore`. Правила — регэкспы по словам с якорем на начало команды, не голая подстрока.
Сломанный ввод или отсутствующий парсер — запрет. Плюс `permissions.deny` на `git push`,
`gh workflow run`, `gh release` и allow-list read-only команд.

**Почему не иначе.** Только `permissions.deny` не ловит `cd x && git push` и переносы строк.
Первая версия матчила подстроку и запрещала `git commit -m "add push subscription"`,
`cat .env.production` и `grep build:prod package.json` — ложное срабатывание учит агента обходить
гейт, и тогда он не ловит уже ничего. Семантический разбор команды сложнее и ошибается в обе
стороны; регэксп по словам — компромисс. Цена, которая осталась: heredoc, в **тексте** которого
есть `git push` в позиции команды, тоже упрётся — такой файл пишется через инструмент Write,
это записано в `CLAUDE.md`.

**Последствия.** Гейт — подстраховка, не разрешение действовать до его срабатывания: рассылки,
запись в боевую базу через приложение и ротацию секретов он не распознаёт, они держатся на
правиле «сначала спроси» в `AGENTS.md`.

## 3. Уведомления о жизни репозитория — отдельный workflow, тексты — чистые функции — 05.09.2026

**Контекст.** Из CI в чат приходили только три деплойных события. Открытый PR, запрошенное ревью,
упавший CI на пуше и влитая ветка были видны только на GitHub, и ревью зависало на «не увидел».
Само деплойное уведомление один раз молчало: трейлер `Co-Authored-By: … <mail>` парсился как
HTML-тег, Bot API отвечал 400, а `curl -s` без `-f` и без чтения ответа выходил нулём.

**Решение.** `notify-telegram.yml` + `scripts/telegram/` (`format.mjs` — чистые функции с
тестами в `pnpm test`, `notify.mjs` — CLI без зависимостей на sparse-checkout). Падения ловятся
через `workflow_run` по именам workflow, а не `if: failure()` в каждой джобе. Деплойный
`notify-telegram.sh` экранирует сообщение, кодирует тело, проверяет ответ и предупреждает
`::warning` при отказе.

**Почему не иначе.** Шаг `if: failure()` в каждой джобе quality.yml забывают при добавлении
джобы; `workflow_run` покрывает новую сам и получает секреты для PR из форка. Уведомление не роняет
CI (`continue-on-error`) — но и не врёт о доставке.

**Что сделать при выкатке.** Секреты репозитория `TG_TOKEN`, `TG_CHAT_ID`, `TG_THREAD_ID` — те же,
что у деплоя. Без них скрипт печатает текст и выходит нулём.

## 4. Lighthouse — по живому `next start`, вес ломает, тайминги предупреждают — 05.09.2026

**Контекст.** Гейта на вес публичных страниц не было: лендинг откатился бы первой же большой
картинкой, и никто бы не заметил до жалобы.

**Решение.** `lighthouse.yml` поднимает монгу, собирает и стартует приложение, гоняет
`treosh/lighthouse-ci-action` по `/`, `/articles`, `/login` (mobile, медиана из 3). В
`lighthouserc.json` вес и CLS — `error`, LCP и категории — `warn`. Запускается только когда
менялось видимое в браузере.

**Почему не иначе.** Статический `staticDistDir` для SSR-приложения не работает. Тайминги на
раннере плавают на ±30 % — как `error` они дают красный CI без регресса. Числа — храповик,
измеренный на бойлерплейте; дочерний проект выставляет свои после первого прогона.

## 5. Публичная часть окружения — в Variables, доктор гейтом перед выкаткой — 05.09.2026

**Контекст.** Всё окружение лежало одним секретом: что именно выкачено, проверялось только
глазами на сервере. Первый деплой стейджа дочернего проекта упал на `MONGO_URI=mongodb://localhost`
внутри контейнера, второй — на `\r` в конце строк секрета, вставленного из Windows-редактора.

**Решение.** Вход `env_public` (вызывающий передаёт `${{ vars.WEB_ENV_PUBLIC_PROD }}`),
дописывается после секрета — публичное побеждает, пересечения печатаются именами, имена,
оканчивающиеся на `_SECRET/_PASSWORD/_TOKEN/_KEY…`, в Variables валят деплой. CRLF снимается с
`::warning`. Вход `doctor_check_enabled` гоняет `pnpm doctor:<env>` по собранному файлу в CI;
доктор при `MONGO_ENABLED`/`REDIS_ENABLED` считает loopback-хост ошибкой
(`config/container-topology.ts`).

**Почему не иначе.** Читать `vars.*` внутри переиспользуемого workflow — значит стейдж и прод
не могут взять разные переменные. «Публичное побеждает» — сознательно: секрет write-only, и через
полгода никто не помнит, что в нём. Молчаливая чистка `\r` оставила бы мину в секрете для
следующего, кто его скопирует.

**Что сделать при выкатке.** Ничего обязательного: пустая Variable = всё по-прежнему из секрета.
`doctor_check_enabled: true` в `prod-deploy.yml` — если доктор красный на боевом env, это
находка, а не ложное срабатывание; выключать флаг только осознанно.

## 6. Деплой-скрипт: хранилища первыми, один бюджет ожидания, отказ pull останавливает — 05.09.2026

**Контекст.** Три первых деплоя стейджа дочернего проекта упали на «core-api failed to become
healthy» без единой строки от контейнера: api стартовал бок о бок со свежей монгой, 60 с холодного
пути кончались до того, как Next начинал слушать. Отдельно `docker pull` из GHCR отвечал `denied`,
код никто не проверял, и compose восемь минут собирал образ на сервере.

**Решение.** `local-containers-run.sh`: включённые redis/mongo поднимаются и ждутся healthy до
api; одна функция `wait_for_container_healthy` с бюджетом 150×2 с, при падении печатает
`docker logs --tail=200`; `pull_core_api_image` останавливает деплой при отказе.

**Почему не иначе.** Порядок в скрипте, а не в compose `depends_on`: mongo и redis опциональны
(внешний кластер), безусловная зависимость подняла бы там лишнюю локальную монгу. Один бюджет
на холодный, зелёный и своп — чтобы разные пути не расходились в тайм-аутах.

## 7. Grafana: пин версии и 43 % бюджета метрик — 05.09.2026

**Контекст.** `grafana:latest` привёз 13.x без предупреждения; Grafana 13 запускает Loki-датасорс
отдельным процессом и на запросе логов достигает ~450 МБ RSS. При 29 % пула на 4 ГБ хосте лимит
был 344 МБ — memcg убивал процесс дважды в минуту, при этом контейнер показывал `OOMKilled=false`.

**Решение.** Образ пинится (`13.2.1`), доля Grafana в `memory-limits.sh` — 43 %, Prometheus
(простаивал на 30 МБ из 249) — 14 %, аналитика и проверка обновлений выключены.

**Почему не иначе.** Аппетит — свойство версии, а не хоста, поэтому «дать больше памяти
серверу» не лечит. Ниже ~3 ГБ стек метрик не помещается вовсе — выключать `metrics_enabled`,
а не ужимать доли.

**Последствия.** Демо-деплой (`server_memory_mb: 2048`) идёт с `metrics_enabled: false`: 43 % от
пула на 2 ГБ — это 254 МБ, ниже пика. `memory-limits.sh` печатает `WARN`, если лимит Grafana ниже
450 МБ, но не клампит: у бюджета ~7 % запаса, молчаливая добавка его переберёт. Дефолт compose без
бюджета — 512 МБ. Включать метрики обратно с реальным объёмом RAM ≥ 4096.

## 8. Правки по адверсарному ревью переноса — 05.09.2026

**Контекст.** Перед коммитом аудита дифф прогнали через независимое ревью (5 направлений, по три
опровергателя на находку): 22 подтверждённых, 1 отклонена. Ниже — те, что меняют поведение, а не
текст.

**Решения.**

- **Mongo получил healthcheck** в `docker-compose.local.yml`: Stage 0 https-пути ждёт `healthy`,
  а сервис без healthcheck не проходит его никогда — каждый холодный деплой с `mongo_enabled: true`
  падал бы через 300 с при уже разобранном стеке. Вариант с `rs.initiate` для реплика-сета не перенесён:
  здесь standalone. `wait_for_container_healthy` теперь падает сразу с внятной причиной, если у
  контейнера нет healthcheck, а не сидит весь бюджет и не пишет «no container».
- **Preflight `docker pull` в воркфлоу до `clean`.** Отказ pull после разборки стека — простой,
  а не медленная сборка, как раньше. Проверка в `local-containers-run.sh` остаётся второй сеткой.
- **Булевы флаги в `config/env.ts` парсятся после деструктуризации.** Дефолт деструктуризации
  срабатывает только на `undefined`, поэтому `FLAG = process.env.FLAG === 'true'` возвращал строку
  `'false'` — truthy — и доктор-гейт отказывал корректно выключенному LLM. Дефолты сохранены:
  `RUM_ENABLED` — true, остальные — false.
- **Шаблон `.env.example` doctor-clean.** Списки OAuth-провайдеров пустые: с
  `yandex,google,github` при `*_ENABLED=0` доктор давал 9 ошибок, и `make setup` на свежей копии
  краснел. Комментарий объясняет три условия включения провайдера.
- **Топология Mongo при sibling-контейнере:** креды обязательны всегда — compose создаёт
  root-пользователя безусловно (`${MONGO_USER:-admin}`), а не «когда задан MONGO_USER». Путь `/admin`
  в URI принимается без `authSource`. IPv6 в скобках парсится.
- **Гейт `guard-external.sh` — регэкспы по словам** (см. §2, обновлено).
- **Гейты:** `gates.mjs` запускает проверки с `cwd` в корне; храповик `eslint-disable` считает и
  тестовые файлы (eslint их линтит) и не падает на отсутствующем каталоге; `check-agent-contract`
  меряет и `AGENTS_RU.md`.
- **`INDEXNOW_API_KEY`** исключён из сетки «секрет в Variables»: он публичен по протоколу.
- **Публичный env в лог сборки печатается именами**, без значений.

**Отклонено.** «`MONGO_ENABLED` / `REDIS_ENABLED` не описаны в env-докe» — это не переменные
приложения, а входы деплоя, которые воркфлоу пробрасывает доктору; описаны в `docs/configure/env-reference.ru.md`
рядом с `MONGO_URI` и в `docs/deploy/ci-notifications-lighthouse.ru.md`.

## 9. Документация по темам с суффиксом языка; env — один шаблон и справочник под гейтом — 06.09.2026

**Контекст.** 33 файла плоско в `docs/`, суффикс `_RU` у половины, английские версии у шести,
README на 490 строк дублировал деплой-раздел. Новому человеку не с чего начать; агенту — не по
чему искать. `.env.example` вырос до простыни комментариев, а `ENV_REFERENCE.md` расходился с ним
и по составу, и по порядку.

**Решение.** `docs/<тема>/<kebab>.<ru|en>.md`: `start`, `configure`, `deploy`, `develop`,
`security`, `agents`, `decisions`, `plans`, `audits`, `roadmaps`. RU — канонический; EN — у входных
документов (README, getting-started, local-development, github-actions, env-reference) и там, где
он уже был. README сокращён до входа. `.env.example` — те же секции и порядок, что в справочнике,
комментарий не длиннее строки; подробности живут в справочнике. Два гейта: `check-docs-structure`
(имена, индекс, живые ссылки во всех `.md`) и `check-env-reference` (паритет имён шаблона и двух
справочников).

**Почему не иначе.** `docs/ru/` и `docs/en/` с зеркальным деревом требуют перевода всех 33
документов ради симметрии — половина из них архивные роадмапы. Генерировать справочник из шаблона —
лишний слой и формат комментариев, который надо соблюдать; ручной справочник под гейтом по именам
дешевле и честнее. Ссылки на `§N` журнала в коде не тронуты: перенумерации нет, сменился только
путь к файлу.

**Последствия.** Новый документ — только в папку темы с суффиксом языка и строкой в индексе, иначе
`pnpm gates` красный. Новая переменная — строка в двух справочниках. Патчи в `patch/` ссылаются на
старые имена и остаются как есть: это история.

## 10. Агент пушит ветки и открывает PR в develop; гейт режет только main и force — 06.09.2026

**Контекст.** §2 запрещал агенту `git push` целиком: `prod-deploy.yml` выкатывает прод на push в
`main`. С переходом на поток `ветка → PR в develop → PR develop → main` полный запрет стал мешать:
каждый PR требовал двух ручных команд владельца, а риск был только в одной ветке.

**Решение.** Push своей ветки и `gh pr create` в `develop` — внутренняя операция, агент делает
сам. `guard-external.sh` режет push, явно нацеленный в `main` (`origin main`, `HEAD:main`), и
любой force-push (`--force`, `-f`, `--force-with-lease`, `+ref`). `permissions.deny` на
`gh workflow run` остаётся: ручной деплой — слово владельца. Правило §2 в остальном без изменений.

**Почему не иначе.** Снять гейт целиком — значит положиться на то, что агент не перепутает ветку в
`-u origin …`. Запретить всё — вернуть ручные команды. Проверка по refspec дешёвая и ловит ровно ту
ветку, которая деплоит.

**Последствия.** Push в `main` бывает только merge-ом PR из `develop` руками владельца.

## 11. Гейт агента: явный пункт назначения у push, тома и бэкапы, честный fail-closed — 12.09.2026

**Контекст.** Внешний аудит потомка (94 находки, план — `docs/plans/backport-hardening.ru.md`)
показал, что §10 закрыл только push с явным словом `main`: голый `git push` с `main` под ногами,
`--all`, `--mirror`, `HEAD:refs/heads/main`, `gh pr merge` и `gh api -X POST` проходили. Ни
одного правила на `docker volume rm` / `compose down -v` — ровно то, чем в потомке потеряли данные
прода. И заявленный «fail closed» был неверен: для PreToolUse коды 126/127 (нет скрипта, нет бита
x) значат «не мешать», то есть потеря файла выключала весь слой молча.

**Решение.** Push разрешён только с явным `<remote> <ветка>`; всё, что берёт ветку из состояния
(`git push`, `origin HEAD`, `@`), и всё широкое (`--all`, `--mirror`, `--tags`, `--delete`) —
запрет. Семейства правил на `gh` (merge, запись через API, административные команды), на тома,
`system prune`, `crontab -r` и удаление бэкапов. Кавычки раскрываются в разделитель, чтобы
`ssh host '…'`, `bash -c` и `eval` не прятали команду. Хук в `settings.json` — обёртка с `[ -x ]`,
гейт `check-agent-gate` в `pnpm gates` следит за битом и обёрткой. Таблица вердиктов —
`scripts/guard-external.test.mjs` в `pnpm test`.

**Почему не иначе.** Семантический разбор shell — ошибки в обе стороны; словарные регэкспы с
якорем на начало команды и таблицей вердиктов — предсказуемо и проверяемо. Цена раскрытия кавычек
названа в `CLAUDE.md`: heredoc с запрещённой командой в тексте упрётся — такие файлы пишутся
инструментом Write.

**Последствия.** Агент пишет `git push origin <ветка>` всегда явно. Автовыкат по push в `main`
остаётся: гейт защищает не пайплайн, а руку агента на нём.

## 12. Пачка B аудита: auth и утечки — что и почему именно так — 13.09.2026

**Контекст.** Пачка B из `docs/plans/backport-hardening.ru.md`: находки, которые меняют
поведение приложения, но не трогают сервер. Каждая — воспроизводимая дыра на нашем HEAD.

**Решения, в которых был выбор.**

- **Proxy получил `matcher`, а `proxyClientMaxBodySize: '200mb'` остался.** Настройка нужна
  только пока proxy буферизует тела на `/api/*`; с matcher он туда не ходит, и лимит ничего не
  ограничивает. Убрать его — отдельный шаг вместе с лимитами загрузки (пачка D), иначе есть риск
  задеть медиатеку.
- **Healthcheck: `db` в теле всегда, 503 — только по флагу `HEALTHCHECK_DB_STRICT`.** Строгий
  режим делает контейнер unhealthy при недоступной базе — это и цель, и риск: короткая заминка
  Mongo на маленьком VPS превращается в снятый апстрим nginx. По умолчанию статус 200, как было,
  плюс `db: fail` в теле и запись в логе; строгость включает владелец на конкретном деплое.
  Причина в теле не отдаётся — роут публичный.
- **`/login` не разлогинивает; вошедшего уводим по `nextPath`.** Альтернатива «показать форму
  вошедшему» бессмысленна. Выход — только `/logout`.
- **Ответ-двойник в «забыли пароль» равен ответу типичного пользователя без MFA.** Полностью
  одинаковыми все ответы быть не могут: пользователю надо сказать, какие факторы вводить.
  Остаточный оракул — «аккаунт есть **и** на нём MFA» — принят: он требует знать адрес и даёт
  только факт наличия второго фактора.
- **MFA challenge одноразовый и со счётчиком, но без привязки к браузеру.** Привязка через
  httpOnly-cookie требует ставить cookie в двух местах (логин и OAuth-редирект) и при любом сбое
  ломает вход по MFA; отложено в «глубже» пачки B до отдельного PR с проверкой на демо.
- **Legacy `POST /auth/register` ограничен, а не удалён.** В репозитории вызывающих нет, но
  снаружи они могут быть: роут оставлен только для ADMIN, с политикой пароля и без подмены cookie
  вызывающего. Удаление — отдельным решением, когда убедимся, что никто не ходит.
- **`JWT_SECRET`: стоп только на пустом или дефолтном, короткий — предупреждение.** У живых
  проектов секреты бывают короче 32 символов; правило, которое останавливает их деплой или старт,
  меняет теоретическую слабость на реальный простой. Пустой/дефолтный — это отсутствие подписи,
  и доктор на нём ошибался и раньше; рантайм-проверка повторяет ровно это правило.

**Общий принцип пачки (после замечания владельца).** Правка не должна ломать работающий деплой
сама по себе: новое строгое поведение — либо предупреждение, либо флаг, который включает
владелец. Стоп — только там, где и раньше был стоп.

**Что при выкатке.** Ничего руками. После выкатки: `curl -sI https://<домен>/profile` показывает
`no-store`; healthcheck отдаёт `{"db":"ok"}`; в DevTools старого бакета `html-v3` нет. Если
захочется строгий healthcheck — `HEALTHCHECK_DB_STRICT=true` в env деплоя.

## 13. Почта: три режима явно, «пропущено» ≠ «отправлено», SMTP не заводим — 13.09.2026

**Контекст.** `sendTransactional` разбирал два режима, всё остальное — включая дефолт `empty` и
опечатку — уходило в консольный провайдер и возвращало `skipped`; вызывающие смотрели только на
исключение, и пользователь видел «код отправлен» без письма. Канал email вычёркивался из события
до доставки, и `login` с единственным каналом email в режиме `console` не оставлял записи вовсе.

**Решение.** `lib/services/email/email-mode.ts` — один разбор режима для сервиса, доктора и
OTP-потоков: `console` (лог; законный dev/stage-режим, коды читаются оттуда), `elastic`
(единственный боевой транспорт), `empty` (почты нет), остальное — опечатка. OTP-потоки принимают
`console` и отвергают `empty` / опечатку / отказ провайдера. Канал уведомления не вычёркивается:
доставка помечает его «пропущено» с причиной, агрегат «все каналы пропущены» — `skipped`.
Доктор — только предупреждения.

**Почему не иначе.** SMTP-провайдер не заводится: по решению владельца Elastic — единственный
боевой транспорт, `console` — для разработки. Опечатка в режиме не роняет старт приложения и не
останавливает деплой: это отчёт доктора и ошибка в логе, а не простой — правило §12. Ответ
«ошибка отправки» вместо «код отправлен» при `empty` — единственное изменение, которое видит
пользователь, и оно честнее прежнего: письма всё равно не было.

**Последствия.** В dev с `console` регистрация и восстановление работают как раньше; в
`/notifications` появляются записи «пропущено: почта не настроена» для событий с единственным
каналом email — это и есть след, которого не хватало.

## 14. Пачка E аудита: пайплайн деплоя — что ужесточено и почему это не ломает выкат — 13.09.2026

**Контекст.** Деплой был «зелёным», когда ssh-скрипт вышел с нулём: 502 от nginx или api в
рестарт-цикле замечали пользователи. Сторонние действия брались с `@master`, `checkout@v2` — с
node12. Вызывающий воркфлоу шёл с `permissions: write-all`, а `GITHUB_TOKEN` и имя актёра
пробрасывались на сервер в двух ssh-шагах, где не использовались. Шаг `find ~ -name '*.tar.gz'
-exec rm` ходил `rm`-ом по всему домашнему каталогу ради мусора одной загрузки. `RUN pnpm run
test` в Dockerfile прогонял ноль тестов (`.dockerignore` исключает `**/*.test.*`) и был зелёным.
`MIGRATIONS_RUN=true` без скриптов миграций молча отвечал «нет ожидающих». Push в `main` с одной
правкой доков перезапускал прод.

**Решение.** Пины по SHA с тегом в комментарии (`ssh-action` v1.2.5, `scp-action` v1.0.0,
`checkout` v6.1.0); `contents: read` + `packages: write` у вызывающего и переиспользуемого
воркфлоу, `id-token` убран; токен раннера на сервер не уезжает; `trap docker logout` в
серверном скрипте — токен GHCR не остаётся в `~/.docker/config.json`. Вместо шага с `find` —
`rm: true` у `scp-action`: свежий `~/app_new` на каждый деплой, ничего за пределами него не
трогается. Смоук после рестарта nginx: `/api/v1/healthcheck` и `/` с раннера, 12 попыток по 10 с;
красный ответ — красный прогон и уведомление, отката нет (стек уже поднят, это доказательство,
а не действие). Тестовый шаг из Dockerfile убран, а `quality` считает выполненные тесты и падает,
если их меньше ста — пустой glob у `node --test` выходит нулём. `MIGRATIONS_RUN=true` без
`migration:show|run:<env>` в образе — ошибка деплоя. `paths-ignore` на push в `main` для доков,
`*.md`, `patch/`, `skills/`, `.claude/`, бюджета Lighthouse и CI-only воркфлоу.

**Почему не иначе.** Смоук включён по умолчанию, но выключается входом `smoke_check_enabled`:
домен, недоступный с раннеров GitHub, — законный случай, а не повод для красного прогона.
`workflow_dispatch` только с `main` через `environment: production` не сделан: это новая сущность
в настройках репозитория и запрет привычного ручного запуска с ветки — решение владельца, не
пачки. Порог в сто тестов, а не «больше нуля»: в суите 243 теста, а glob, потерявший одну папку,
даёт не ноль, а меньше — и это тоже поломка.

**Что при выкатке.** Ничего руками: секретов не добавляется, поведение на сервере — то же плюс
`docker logout` в конце. Первый прогон после merge покажет шаг «Smoke check from outside»; если
он красный при живом сайте — смотреть DNS/443 с раннера, а не откатывать.

## 15. Пачка D аудита: медиа — размер до тела, тип по байтам, приватные ассеты, лимит nginx — 13.09.2026

**Контекст.** `/cdn/<id>` отдавал любой ассет 302-редиректом без проверок, мусорный id давал
CastError и 500. Роут загрузки читал `formData()` до проверки размера, а nginx пропускал 200 МБ на
любой запрос, включая анонимные — проверка «не больше 200 МБ» в коде защищала память уже после
того, как тело в неё легло. Тип файла брался со слов клиента (`file.type` из формы), `resourceType`
из формы перекрывал определение по содержимому. Список медиатеки отдавал `toObject()` целиком:
`createdBy` (файл ↔ человек) и `originalUrl`/`providerFileId` (адрес в хранилище в обход
`/cdn`). CDN — Uploadcare, байты картинок всегда с `ucarecdn.com`, поэтому SVG для нас P2, не P0.

**Решение.** `Content-Length` до `formData()`: больше лимита — 413; нет заголовка — старый путь,
не отказ. nginx: 10m по умолчанию, 200m — вложенный `location = /api/v1/media/upload` внутри
`location /`. Вложенный, а не соседний: `proxy_set_header`/буферы/таймауты наследуются, дублировать
не нужно; `set` не наследуется (rewrite-модуль исполняет только внутренний блок — проверено живым
прокси в контейнере: без повтора `set` — 500 «invalid URL prefix»), поэтому девять `set` повторены
дословно. Тип — по первым 512 байтам: слот картинки берёт только байты картинки (растр или SVG),
никакой слот не берёт HTML; видео/аудио/документы сигнатур не имеют — остаётся заявленный тип.
Хранилище возвращает свой `mime_type`; расхождение с нашим — файл удаляется, документ не
создаётся. Модель: `purpose` (`cms`/`user`) и `visibility` (`public`/`private`) с дефолтами,
совпадающими с существующими документами; `/cdn` — 404 для приватного и для кривого id;
авторизованная отдача `GET /api/v1/media/[id]/file` (владелец или админ, `private, no-store`,
sandbox-CSP, `attachment` для всего, что не растр). Ответы медиа-API — явный DTO без `createdBy`,
`originalUrl`, `providerFileId`; список и удаление библиотеки — только `purpose != user`.

**Почему не иначе.** Запрет SVG в загрузке не сделан: он в списке `accept` поля, отдаётся с чужого
origin и не исполняется в нашем — запрет сломал бы логотипы ради ничего. Белый список сигнатур для
видео/аудио/документов не заведён: список неполный по природе, а ложный отказ ломает реальную
загрузку; HTML и SVG в этих слотах отвергаются, остальное — как было. Лимит 10m, не 1m: тело
статьи с разметкой в мегабайты — законный запрос. Автоудаление прежнего файла при замене в CMS не
сделано намеренно: медиатека — библиотека для повторного использования, старая картинка статьи —
не сирота (см. план D). Отсутствующий `Content-Length` не отказ: клиент с chunked-телом работал
вчера и должен работать сегодня, nginx его всё равно режет.

**Что при выкатке.** Ничего руками: шаблоны nginx подхватываются деплоем, миграции нет.
Проверка после выкатки: `curl -i https://<домен>/cdn/not-an-id` → 400 без 500 в логах; загрузка
PNG из редактора работает как раньше; `curl -X POST --data-binary @20mb.bin
https://<домен>/api/v1/llm/chat` → 413 от nginx, в логах приложения запроса нет.
