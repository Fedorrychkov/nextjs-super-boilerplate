# Правила ревью

Для людей и для ИИ-ревьюеров (Claude Code `/code-review`, Codex, Cursor). Ревью читает PR
относительно `develop`. Правила проекта — в `AGENTS.md`, здесь только то, как их проверять.

## Что такое finding

Замечание = **строка diff + реальный сценарий, в котором это ломается**. «Можно лучше» без
сценария — не finding, а предложение, и оно идёт отдельным списком в конце.

Формат:

```
[P1] lib/services/auth.service.ts:42 — refresh-токен не привязан к сессии, отзыв сессии не инвалидирует access.
Сценарий: пользователь жмёт «выйти со всех устройств» → старый access живёт до истечения.
```

## Приоритеты

| | Что это | Что делать |
|---|---|---|
| P0 | Ломает прод для пользователей, теряет данные, открывает доступ не тому | Блокирует merge |
| P1 | Неверное поведение в реальном сценарии, регрессия, утечка секрета или серверного поля в клиентский DTO | Блокирует merge, если автор не обосновал |
| P2 | Техдолг, читаемость, производительность без измерений | Комментарий, не блокирует |

Ревьюер оставляет **COMMENT**, не REQUEST_CHANGES: решение о merge принимает владелец репо после
зелёного CI.

## Не сообщай то, что уже ловит CI

| Проверка | Где | Что ловит |
|---|---|---|
| `gates` | `quality` | `check-agent-contract` (размер `AGENTS.md`, тонкий `CLAUDE.md`), `check-eslint-disable-ratchet` (число `eslint-disable` не растёт) |
| `lint` | `quality` | ESLint: сырые `<input>/<select>/<textarea>` вне `src/components/ui`, голые `<span>`, порядок импортов, prettier |
| `typecheck` | `quality` | `tsc --noEmit`, strict |
| `test` | `quality` | `node --test` по `*.test.ts` и `scripts/telegram/*.test.mjs`, без инфраструктуры |
| `gitleaks` | `Secret scan` | Новые секреты в отслеживаемых файлах |
| `lighthouse` | `Lighthouse` | Бюджеты `/`, `/articles`, `/login` по живому `next start`: вес страницы, JS, картинки, шрифты, CLS ломают; LCP и performance предупреждают. Только при изменениях `src/**`, `public/**`, `next.config.ts` |
| `notify-telegram` | `Notify Telegram` | Ничего не проверяет: шлёт открытие PR, запрос и результат ревью, падения CI и Secret scan, merge; цифры Lighthouse шлёт сам `lighthouse.yml` |

## На что смотреть в первую очередь

1. **Целостность scope.** PR делает то, что написано в заголовке, и ничего «заодно».
   Форматирование чужих файлов, переименования мимо задачи — P2 с просьбой вынести.
2. **Права.** Новый роут — какая обёртка (`withAuth` / `withAdminAuth` / `withApiTokenOrAuth`
   и scope)? Новый изменяющий эндпоинт — проверка владельца ресурса, не только роли. Публичный
   DTO — нет `email`, хэшей, серверных полей.
3. **Секреты и клиент.** Серверная переменная не утекла в `NEXT_PUBLIC_*`; ключи провайдеров не
   логируются; новая переменная есть в `.env.example` и `docs/ENV_REFERENCE.md`.
4. **Rate limit.** Новый публичный роут обёрнут `withGlobalRateLimit` или профильным лимитером.
5. **Тесты.** Новая чистая логика без теста — P1 для средней и крупной задачи. Тест, который не
   может упасть (проверяет мок, а не поведение), — P1.
6. **Состояния экрана.** Новый экран без loading / error / empty — P2. Ключи i18n добавлены в оба
   словаря (`src/lib/i18n/messages/{ru,en}.ts`).
7. **Документация.** Изменился процесс, контракт, правило — обновлён `AGENTS.md` или `docs/`;
   решение, которое захочется отменить, — запись в `docs/DECISIONS_RU.md`.
8. **Деплой.** Тронуты `.github/workflows/**`, `scripts/local-containers-run.sh`,
   `docker-compose.local.yml` — в PR написано, что должен сделать владелец при выкатке.

## Что не считается finding

- Стиль, который не ловит линт, если он не мешает читать.
- «Я бы сделал иначе» без сценария поломки.
- Просьба переписать старый код, которого PR не касался.

Ревью, где реализован каждый пункт, неудачно; ноль findings — хороший результат.
