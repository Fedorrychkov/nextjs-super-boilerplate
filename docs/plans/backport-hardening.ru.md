# Обратный перенос находок аудита: гейты, auth, почта, медиа, деплой, бэкапы

**Дата:** 12.09.2026. **Состояние:** в работе (пачка A сделана, B–G ждут). Источник — внешний
аудит потомка бойлерплейта (документ `BACKPORT_BOILERPLATE_RU.md`, вне репозитория): 94 находки,
снятые с нашего HEAD `4f46410`, каждая со строками, диффом и способом проверки. Выборочная сверка
подтвердила точность; статусы ниже — снимок на дату, перед правкой сверяйся с кодом.

Цель плана — не переделать всё разом, а разложить на пачки по риску: что меняет только
инструменты агента и CI, что меняет поведение приложения, а что трогает живой прод, который
выкатывается автоматически с `main`. Автовыкат остаётся; порядок пачек защищает именно его.

## Что вне задачи

- Роадмапные фичи (SMTP-провайдер, off-site бэкапы в S3, внешний сторож свежести, автопроверка
  восстановления, Telegram-канал администратора) — заводятся отдельными планами, когда дойдёт
  очередь; здесь только место в порядке.
- Перенос в потомков: у них свои состояния, переносить копированием после закрытия здесь.

## Пачки и порядок

### A. Агентский гейт и гейты качества — сделано 12.09.2026

Без рантайм-риска: трогает только `.claude/`, `scripts/`, husky, eslint severity и доки.

- Гейт: голый `git push` / `--all` / `--mirror` / `HEAD` / `refs/heads/main`, `gh pr merge`,
  `gh api` с записью, `gh workflow|release|secret|variable|repo`, `docker volume rm|prune`,
  `compose down -v`, `system prune`, `crontab -r`, удаление бэкапов, `dropDatabase(`; обёртки
  `ssh '…'` / `bash -c` / `eval` через раскрытие кавычек. Таблица вердиктов —
  `scripts/guard-external.test.mjs` в `pnpm test`.
- «Fail closed» честно: хук в `settings.json` — обёртка с `[ -x ]`, гейт `check-agent-gate`.
- `check-agent-contract`: двойник необязателен, дрейф объёма > 25 % — падение; пути от корня.
- Храповик без baseline — падение, а не молчаливая запись.
- pre-commit: `typecheck` + `lint-staged` (`eslint --fix --max-warnings 0` по staged), без
  прохода по репозиторию.
- Планы: `docs/plans/<домен>-<что>.ru.md`, свой индекс в `docs/plans/README.md`, гейт структуры
  знает про него.
- `no-restricted-syntax` → `error` (нарушений 0); доки агентов без ссылок на несуществующие
  обёртки и старые пути.

### B. Приложение: auth и утечки (P0/P1, низкий радиус) — сделано 13.09.2026

Поведение меняется, но проверяется юнитами и на демо; прод-инфраструктуру не трогает. Из
таблицы ниже сделано всё; legacy register оставлен только админу без подмены cookie; healthcheck
отдаёт `db` в теле, 503 — по флагу `HEALTHCHECK_DB_STRICT`; короткий `JWT_SECRET` — только
предупреждение. Принцип: новое строгое поведение — предупреждение или флаг владельца, не стоп.
Из «глубже»: одноразовый MFA challenge со счётчиком и счётчик
TOTP в восстановлении — сделано; claim типа токена, роль из БД, привязка OAuth state к браузеру и
`verified` email провайдера — остаются.

| Находка | Что менять | Риск для работающего |
|---|---|---|
| Access-токен в заголовке **ответа** `Authorization` + нет `matcher` у proxy | Убрать заголовок из ответа (он нужен только в `request.headers` для роутов), добавить `export const config = { matcher }` | Проверить, что API-роуты читают токен из cookie/пробросенного request-заголовка, а не из ответа |
| Полные заголовки в логах API | Редактировать `cookie`, `authorization`, `x-api-token`; URL без query | Нет |
| Оракул email/пароля первого админа в sign-up | Одинаковый ответ для любого адреса; первый админ создаётся только на старте | Проверить сценарий первого входа админа на свежей базе |
| Open redirect `nextPath` (`/login`, `/refresh`, `/logout`, OAuth) | Одна функция `safeNextPath`: только `/…`, не `//`, не `/\`, кодирование при склейке | Нет |
| `/login` всегда делает logout (logout-CSRF) | Logout только по явному действию | Проверить сценарий «зашёл на /login уже залогиненным» |
| Восстановление пароля раскрывает регистрацию | Единый ответ | Нет |
| Legacy `POST /auth/register` | Выключить или оставить только за админом, без подмены cookie | Проверить, кто им пользуется (MCP? скрипты?) |
| MFA challenge многоразовый | Одноразовый, счётчик попыток, TTL | Нет |
| `code`/`state` OAuth в логах | Не логировать | Нет |
| Healthcheck 200 при недоступной Mongo | `ping` в healthcheck; учесть, что compose/deploy ждут `healthy` — при падении Mongo api станет unhealthy, это и есть цель | Blue/green и Stage 0 в деплое опираются на healthcheck: проверить на демо |
| Service worker кеширует HTML закрытых страниц | Не кешировать `/profile`, `/admin/*`, `/api/*`; network-only для HTML за auth | Проверить офлайн-режим на демо |
| `robots.ts` disallow только для `*` | Правила для всех групп | Нет |
| Дефолтный `JWT_SECRET` в prod | Doctor и старт падают в production с плейсхолдером | Нет (на демо секрет задан) |

Глубже (P1, менять осознанно, по одному PR): claim типа токена (`typ: access|refresh`), роль и
статус из БД, а не только из JWT; OAuth state привязать к браузеру (cookie-nonce); email
провайдера только `verified`; link/unlink под TOTP.

### C. Почта (P0/P1)

- Неизвестный `EMAIL_SEND_MODE` — падение на старте и в doctor, а не молчаливый `console`.
- Отправка кода регистрации/восстановления проверяет результат провайдера; пользователю —

- Событие с единственным каналом email в режиме `console` создаёт запись уведомления.
- SMTP-провайдер — отдельный план (новая зависимость).

### D. Медиа (P0/P1)

- `/cdn/[...variants]`: авторизация и владелец для приватных ассетов (публичные — как сейчас).
- Проверка размера до чтения тела; `client_max_body_size` на нужные location.
- SVG/ICO: не отдавать с нашего origin как исполняемое — `Content-Disposition: attachment` или
  запрет типа; MIME по сигнатуре, не по заявке клиента.
- Замена файла удаляет прежний; пользовательские файлы не попадают в медиатеку CMS.

### F. Сервер и бэкапы (P0/P1) — трогает живой прод, только с runbook

Здесь «не сломать работающее» — главный критерий. Каждый пункт с планом отката и проверкой на
демо-сервере до merge в `main`.

- **Имя тома данных** сейчас зависит от каталога проекта; закрепить `name:` — но на живом сервере
  это **новый пустой том**. Порядок: дамп → остановить → `docker volume create <new>` и копия
  данных → поднять → проверить → удалить старый. Плюс гард в деплое: свежий том при непустой
  базе в дампах — стоп.
- `stop_grace_period` для mongo/redis; холодный путь не гасит хранилища дважды; cron бэкапа не
  совпадает с окном деплоя (лок или пауза).
- Бэкап: залипший лок — не «успех», а ошибка с алертом; дамп меньше N % от предыдущего —
  не вытесняет годные; пароль не в argv; дампы `0600`; точка отката перед деплоем и перед
  restore; рассинхрон кредов — падение деплоя; дефолт `mongo_backup_enabled: true`.
- Логи контейнеров `2g×3` → разумные лимиты; `docker.sock` в certbot и ночной рестарт nginx;
  тома наблюдаемости вне каталога деплоя; слабые дефолтные креды mongo → обязательные;
  `/nginx_status` и IPv6 в rate limit; отладочные заголовки и `server_tokens off`; пин образов.
- FAQ и README: убрать совет «удалить том, если не уверены».

## Критерий приёмки

Каждая пачка — свой PR в `develop` с прогоном `pnpm gates && pnpm test && pnpm typecheck &&
pnpm lint`, для B–D — проверка сценария на демо после выкатки, для F — runbook в PR и откат
описан до merge. Находка закрывается только когда воспроизведена «до» и не воспроизводится «после».

- A: ничего.
- E: секреты `PROD_WEB_SSH_KEY` / `PROD_WEB_SSH_FINGERPRINT` — когда захочется перейти на ключ;
  без них деплой идёт по паролю, как раньше.
- F: миграция тома и первый бэкап новой схемы — руками владельца по runbook, в окно без
