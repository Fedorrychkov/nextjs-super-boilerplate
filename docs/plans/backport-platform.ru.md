# Перенос из потомка: безопасность, публикация по расписанию, воркер, метрики, настройки, админка, деплой

**Дата:** 15.11.2026. **Состояние:** в работе. Источник — потомок бойлерплейта: форк от `0344406`
(13.09.2026), за два месяца выросший почти вдвое. Он ведёт свой список дефектов бойлерплейта и
помечает в журнале правки, полезные всем. Этот план собирает оба списка плюс общие механизмы,
которые там выросли, и раскладывает их на пачки — по PR в `develop` на каждую.

## Решения владельца (15.11.2026)

- **Облик потомка не берём.** Переносим механизм токенов (источник → CSS-переменные → гейт
  сверки), палитра остаётся нейтральной; внешний вид и UX бойлерплейта улучшаются отдельно.
- **Метрики — фасад со сменными приёмниками:** по умолчанию в логи; в коллекцию Mongo проекта;
  в PostHog; свой адаптер подключается без правки ядра.
- **Настройки платформы — да.** Новые ручки живут там, текущие env не расширяем и не ломаем.
- **4 ГБ heap для сборки — не навязываем:** боевой сервер 2 ГБ; размер heap — параметр того,
  кто разворачивает, в документации.
- **Бэкапы — выбор места назначения:** по умолчанию как сейчас (тот же хост); опционально любое
  S3-совместимое хранилище или другой сервер по SFTP. Это настройки деплоя (входы и секреты
  воркфлоу), не env приложения.
- **Blue/green и деплой — улучшаем**, с проверкой на локальном стенде до merge.

Правило совместимости из пачки B прежнего плана действует: новая строгость — предупреждение или
флаг, стоп — только там, где стоп уже был; живые сессии не обрываются.

## Пачки

### 1. Безопасность и токены — сделано 15.11.2026 (журнал §17)

| Что | Как без поломки |
|---|---|
| Axios-интерсептор пишет все заголовки (cookie с токенами) на info | Логировать метод и путь |
| Refresh принимается как Bearer: в JWT нет `typ` | Новые токены с `typ`; старый токен без `typ` с жизнью длиннее access-TTL — это refresh, как Bearer отвергается; старый access доживает свой час |
| Refresh в базе открытым текстом | В поле `token` пишется `h:<sha256>`; поиск по хешу и по старому значению; старые строки перехешируются при ротации и фоновым проходом на старте. Индекс и схема не меняются |
| `JWT_REFRESH_EXPIRES_IN` по умолчанию 182 дня при cookie 7 дней | Действующий срок = min(env, срок cookie): для пользователя ничего не меняется (простой > 7 дней = выход), утёкший токен живёт 7 дней, а не полгода |
| Роль и статус в API берутся из JWT (понижение действует до часа); `RefreshToken.exists` на каждый запрос | Один снимок «сессия + роль + статус» из базы с кэшем 30 с в Redis, сброс при смене роли/статуса и отзыве сессий |
| Секрет TOTP уходит на `api.qrserver.com` для QR | QR рисуется в браузере |
| Фильтр аудита молча не работает для `mcp_oauth_*`, `machine_access_*` | Дописать в список действий |
| CSP: `unsafe-eval`, хосты Метрики/GTM всегда, `upgrade-insecure-requests` и в dev | Сборщик CSP в коде: хосты аналитики — только когда она включена; строгая политика рядом в report-only + приёмник отчётов; `upgrade-insecure-requests` только в проде |
| `NEXT_PUBLIC_*` из env деплоя уходит в сборку без списка | Гейт: публичные имена — только из списка в репозитории |

### 2. Гигиена и однострочники

- Планировщик воркера на Job Schedulers BullMQ (`getRepeatableJobs` удалён в BullMQ 6).
- Пины всех `uses:` по SHA, gitleaks по digest, гейт `check-actions-pinned`.
- Гейт ссылок с якорями (сейчас проверяются только файлы).
- IndexNow: `keyLocation` указывает на `/indexnow.txt`, которого нет — роут.
- Даты статьи в meta/JSON-LD выводятся как `[object Object]`; `og:locale:alternate` — только
  языки, которые у статьи реально есть.
- Таймаут Elastic Email, тосты не глотают клики, `closable`/`bare` у диалога и прокрутка только
  тела, `data-theme` в ThemeProvider, `color-scheme` через `.dark`, список уведомлений без
  служебных полей, порционный рендер экрана переводов, `?q=` в списке пользователей,
  `InfiniteList`, защита от цикла перезагрузок после неудачного refresh.

### 3. Отложенная публикация статей

Перенос из форка (поле `scheduledAt`/`scheduledBy`, задача воркера раз в минуту с атомарным
захватом, IndexNow и уведомление после публикации, блок в редакторе, MCP-тул
`schedule_article`) с исправлением пяти слабых мест форка: время в прошлом отвергается;
ревизия не помечается подтверждённой, если захват не удался; снятие с публикации отменяет
расписание; уведомление на языке планировавшего; отрицательный кэш для отсутствующих статей.

Состояния статьи не меняются (`draft | published | unpublished`): «запланирована» = не
опубликована и `scheduledAt != null`.

| Состояние × событие | запланировать | отменить | наступило время | опубликовать руками | снять с публикации | правка ревизии |
|---|---|---|---|---|---|---|
| draft / unpublished | ставит время (только будущее) | — | — | публикует | — | — |
| draft + время | меняет время | снимает | публикует, если ревизия цела | публикует, снимает время | — | захват промахнётся, следующий тик |
| published | отказ | — | — | — | снимает и время | — |

### 4. Воркер как платформа

Слой очередей (определение отдельно от обработчика, повторы, идемпотентный `jobId`, хвосты
`removeOnComplete/Fail`), гейт «у каждой очереди есть обработчик», отметка «воркер жив» в базе и
поле `worker` в healthcheck (статус ответа не зависит от воркера), доставка уведомлений через
очередь с арендой и повторной постановкой, задача хранения данных (история доставки — 90 дней).

### 5. Настройки платформы

Реестр в коде (схема, значение по умолчанию, группа, `sensitive`, `secret`, диапазон, варианты),
значения в Mongo (кто и когда, прежнее значение), кэш 60 с в Redis со сбросом при записи, падение
базы или неверное значение → значение по умолчанию, аудит каждой записи, секреты в AES-GCM на
подключе HKDF от одного ключа шифрования, админ-экран с редактором по типу и разделами. Подписи
— из i18n по ключу настройки, без растущего `switch`. Существующие env не переносятся.

### 6. Метрики

Фасад `metrics.track(event, props)` / `metrics.error(err)` с закрытым списком событий; приёмники:
`log` (по умолчанию), `mongo` (коллекция проекта + экран в админке), `posthog`, свой — через
регистрацию адаптера. Выбор приёмника — настройка платформы. Клиентский трекер с очередью и
`sendBeacon`, приём `/api/v1/ev/batch` с лимитом, отлов ошибок сервера (500 из обработчика API,
финальный провал задачи воркера) и клиента (`window.onerror`, `unhandledrejection`, свои
`error.tsx` и `global-error.tsx` — в форке их отправки нет). Вычистка email/токенов/id из текста,
не чаще раза в 5 минут на одну ошибку, без IP. Обзор `/admin`: здоровье базы, воркера, приёмника.

### 7. Админка, токены и UX

Оболочка админки с группами меню, каркас страницы, пустые состояния, `Switch`, `InlineInput`,
`FilePicker`, поиск человека, обзор; механизм токенов (`tokens.json` → CSS-переменные → гейт
`--check`) с нейтральной палитрой; страницы ошибок и статусов; собственный проход по UX
бойлерплейта (не облик потомка).

### 8. Деплой и бэкапы

Blue/green без 502 при переключении (новый контейнер встаёт под именем сервиса до остановки
старого); certbot без Docker-сокета (nginx перезагружается по файлу-маркеру); срок хранения логов
контейнеров; место назначения бэкапа на выбор (тот же хост / S3-совместимое / SFTP) через
одноразовый контейнер rclone, ключи через env, а не argv; провал выгрузки — красный прогон.

## Что вне задачи

Доменные сущности потомка и его облик; APNs/FCM (у бойлерплейта нет мобильного клиента); домены по
языку статьи (завязаны на настройки потомка); согласие на аналитику в нативных клиентах; барьер
записи при слиянии аккаунтов — особенность потомка.

## Критерий приёмки

Каждая пачка — PR в `develop` с зелёными `pnpm gates`, `pnpm test`, `pnpm typecheck`,
`pnpm lint`, записью в журнале решений и строкой в CHANGELOG. Для пачек 1, 3, 8 — проверка на
локальном стенде (`make up-local`) с описанием в PR: живая сессия, выпущенная до правки,
продолжает работать после неё.

## Что при выкатке

Описывается в PR каждой пачки. Известно заранее: пачка 1 не требует действий (миграция хешей
refresh идёт сама); пачка 5 добавляет ключ шифрования — читается и прежнее имя
`MFA_ENCRYPTION_KEY`, так что без правки env; пачка 8 — новые секреты только для тех, кто
включает выгрузку бэкапа наружу.
