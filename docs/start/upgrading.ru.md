# Обновление форка и проверка релиза

Шаблон обновляется отдельно от прикладного продукта. Сначала выберите проверенную
ревизию, затем переносите изменения в рабочую ветку и просматривайте diff.
Наличие исправления в develop ещё не означает, что оно работает на опубликованном демо.

## Перед обновлением

1. Зафиксируйте свои изменения и запишите текущую рабочую ревизию приложения.
2. Прочитайте журнал изменений и решения выбранного обновления. Проверьте новые
   переменные, изменения схемы данных, флаги и совместимость зависимостей.
3. Подготовьте проверенную резервную копию перед изменениями данных. Сам перенос
   исходников не является разрешением на миграцию или восстановление боевой базы.

Для обычного Git-форка добавьте upstream на репозиторий шаблона и получите его историю
через fetch. Выберите нужные коммиты и перенесите их в отдельную ветку через cherry-pick,
либо подготовьте merge выбранной ревизии с ручным разрешением конфликтов.
Не подменяйте product.ts, конфигурацию авторизации и настройки инфраструктуры
вариантами демо без проверки: это настройки конкретного приложения.

Монорепа с git subtree требует собственного порядка обновления. Не запускайте
init-project.sh повторно и не делайте обычный merge корня шаблона в корень такой монорепы.

## Проверки

```bash
pnpm install --frozen-lockfile
pnpm gates
pnpm lint
pnpm typecheck
pnpm test
```

Запустите локальное приложение и проверьте затронутые сценарии: вход, публичные
страницы, редактор и публикацию, загрузку медиа и интеграции. Набор зависит от diff.
Сборка с локальными настройками проверяется отдельно. Зелёные unit-тесты не
подтверждают исправность провайдеров OAuth, доставки почты, платежей или внешней инфраструктуры.

## Как обновляется демо этого репозитория

Рабочие PR вливаются в develop. Владелец проверяет релизный PR develop → main.
В текущем prod-deploy.yml push в main запускает деплой, кроме исключённых
документационных путей; ручной workflow_dispatch тоже является выкаткой.
Открытие PR само по себе ничего не выкатывает. Изменение deploy workflow во форке
требует отдельной проверки его триггеров и секретов.

После выкладки проверьте домен и конкретное исправление. Например, ответ на запрос
с искусственным cookie accessToken=local-canary не должен содержать его в заголовке
Authorization; robots.txt должен сохранять запреты служебных путей для именованных
ботов. Не используйте настоящие токены в командах проверки и не публикуйте cookies.

## Если результат отличается

Сверьте ревизию выкладки с принятым PR, статус deploy job и конфигурацию домена.
Не запускайте миграции повторно и не восстанавливайте Mongo автоматически.
Откат приложения и откат данных — разные операции с отдельными последствиями.
