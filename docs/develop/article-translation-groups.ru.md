# Связка статей по языкам (translation group) и SEO-пайплайн

Цель: **не объединять** контент разных языков в одну запись `Article` / одну ревизию, а добавить **расширяемую связку** (RU, EN, будущие локали) и корректно обновить **sitemap, метаданные страницы, JSON-LD, RSS, IndexNow** без смены базового URL `/article/:slug`.

### Принципы: без жёсткой валидации, на откуп редактору

Связка по языкам и SEO вокруг неё — **опциональное улучшение**, а не обязательный режим работы CMS.

| Сценарий | Поддержка |
|----------|-----------|
| Опубликовать только RU, английской версии ещё нет | Да: `translationGroupId` отсутствует или в группе одна статья — hreflang только не нужен / не выводим до появления второй опубликованной версии. |
| Позже добавить EN и опубликовать отдельно | Да: обычный `PUT` публикации; после публикации второй версии в группе обновляются **alternates** и sitemap для **обеих** URL (ревалидация соседей). |
| Постепенно добавлять DE, TR, … | Да: в любой момент новая статья с тем же `translationGroupId` + своим `locale`. |
| Сначала всё в draft, потом **одной кнопкой** опубликовать группу | Да: **удобство** (вариант B в п. 5.4), не замена обычной публикации. |
| Старые статьи уже в проде без группы | Да: **ничего не делать** — как сейчас, без `translationGroupId`. |
| Две старые статьи RU+EN «вручную признать переводами» | Да: админка **«Связать»** — выставить один общий `translationGroupId` (и корректные `locale`) без пересоздания контента. |
| Ошибочно связали / хотят развести | Да: **«Отвязать»** — сброс `translationGroupId` (и при необходимости `locale`) у выбранных статей; SEO возвращается к автономным URL. |

**Не делаем по умолчанию:** блокирующую публикацию одной локали «пока не готовы все», обязательные списки локалей, принудительный групповой выпуск. Решение о порядке и полноте выпуска — **редактор / админ**; продукт только даёт инструменты (связь, групповая кнопка, SEO при любом составе группы).

---

## 1. Модель данных (Mongo / `lib/db`)

На коллекции **`Article`** (рядом со `slug`, `status`, …):

| Поле | Тип | Назначение |
|------|-----|------------|
| `translationGroupId` | `string \| null` | UUID одной «логической» публикации на всех языках. `null` = нет связки (как сейчас). |
| `locale` | `string \| null` | BCP-47 (`ru`, `en`, `de`, …). Должен совпадать с `metadata.seo.language` у текущей опубликованной ревизии или задаваться при сохранении и валидироваться. |

Индексы:

- `{ translationGroupId: 1, status: 1 }` — быстрый поиск соседей по группе среди опубликованных.
- Опционально уникальность `{ translationGroupId: 1, locale: 1 }` при `translationGroupId != null`, чтобы в одной группе не было двух `ru`.

Ревизии и SEO **как сейчас**: у каждой языковой статьи свой `ArticleRevision` со своим `metadata.seo` (title, canonical, og, `language`).

## 2. Общий серверный хелпер (рекомендуется один раз вынести)

Например `~/lib/seo/articleTranslationSiblings.ts` (название условное):

- Вход: `translationGroupId`, опционально «текущий `articleId`», фильтр `PUBLISHED` + `PUBLIC` + `slug` + `noindex !== true` по текущей ревизии.
- Выход: список `{ slug, locale, canonicalAbsoluteUrl }` для всех опубликованных соседей в группе.

Его используют:

- `generateMetadata` в `src/app/article/[...slug]/page.tsx` (и при необходимости preview);
- `getPublishedPublicSitemapRoutes` / `mapArticlesToSitemap` в `src/lib/seo/sitemap.ts`;
- обработчик публикации в `src/app/api/v1/article/update/route.ts` для расширения списка URL в IndexNow.

Так не дублируете запросы к Mongo и одну и ту же политику «кого считать альтернативой».

## 3. По файлам

### `src/app/article/[...slug]/page.tsx` (`generateMetadata`)

- После загрузки payload по `slug` (или по id из кэша): если у статьи есть `translationGroupId`, вызвать хелпер соседей.
- В объект `Metadata` добавить **`alternates.languages`**: ключи — BCP-47 (`ru`, `en`, …), значения — **абсолютные** URL каноник соседей (те же правила, что `resolveArticleCanonicalUrl` + slug).
- Добавить **`x-default`**: на основной язык сайта (`seoConfig.defaultLocale`) или явная настройка в env — зафиксировать в коде один раз.

Google ориентируется и на `<link rel="alternate" hreflang>`, которые Next отдаёт из `alternates.languages`, и на sitemap (ниже); дублирование **нормально**.

### `src/lib/seo/jsonld.tsx` (`getArticleJsonLd`)

- **Обязательное минимум:** уже есть `inLanguage` по языку страницы — достаточно для базовой семантики.
- **Улучшение (опционально):** если переданы соседи, добавить в JSON-LD поля Schema.org уровня `CreativeWork`, например связи переводов (`workTranslation` / `translationOfWork` — уточнить под актуальную схему schema-dts). Это **не замена** hreflang в `<head>`.

### `src/lib/seo/sitemap.ts` + `src/app/sitemap.ts`

- В `getPublishedPublicArticlesForSeo` в `.select()` добавить `translationGroupId`, `locale` (если храните на `Article`).
- После получения списка статей: сгруппировать по `translationGroupId` (игнорировать `null`).
- В `mapArticlesToSitemap` для каждой записи, если в группе **≥ 2** опубликованных публичных URL с разными локалями, для объекта sitemap задать **`alternates.languages`** (формат [Next.js Sitemap](https://nextjs.org/docs/app/api-reference/file-conventions/metadata/sitemap#generate-a-localized-sitemap)) — те же URL, что в `generateMetadata`.
- Статические маршруты в `getStaticRoutes()` **не трогаются**.

`src/app/sitemap.ts` менять не обязательно, если вся логика остаётся в `getPublishedPublicSitemapRoutes`.

### `src/app/robots.ts`

- Менять **ничего не нужно**, если языковые версии остаются под тем же `/article/...` без новых запрещённых префиксов.

### `src/app/rss.xml/route.ts`

- RSS 2.0 **не стандартизирует** hreflang на `<item>`. Практичные варианты:
  - **Минимум:** оставить **по одному `<item>` на URL** (как сейчас) — для каждой языковой статьи отдельная запись; агрегаторы видят разные записи.
  - **Улучшение:** в описание или расширение канала добавить человекочитаемую строку «Другие языки: …» или подключить модуль Atom 1.0 с `xml:lang` на entry (отдельный роут `atom.xml` — по желанию).
- При желании вынести `<language>` канала в динамику или оставить `seoConfig.defaultLocale` — на индексацию статей это почти не влияет.

### `src/lib/seo/indexing.ts` + `src/app/api/v1/seo/indexnow/route.ts`

- **API IndexNow** уже принимает массив URL — менять контракт не нужно.
- В **`src/app/api/v1/article/update/route.ts`** при `shouldIndex` и успешной публикации/обновлении: кроме `canonicalUrl` и `defaultPublicUrl` текущей статьи, добавить **канонические URL всех опубликованных соседей** той же `translationGroupId` (через тот же хелпер), в `Set`, затем `notifySearchEngines`. Так поисковики быстрее подхватывают обновлённый кластер hreflang при правке одной версии.
- Аналогично при **снятии с публикации** одной версии: имеет смысл снова пинговать оставшиеся URL группы (опционально), чтобы картина альтернатив обновилась.

### `src/app/api/v1/seo/notify/route.ts`

- Без изменений; вызывающий сам передаёт полный список URL.

---

## 4. Кэш и ревалидация

- При обновлении статьи уже вызываются `revalidatePath('/sitemap.xml')` и `revalidatePath('/rss.xml')`.
- Если добавите `alternates.languages` на **HTML** других соседей, при публикации одной версии стоит **revalidateTag** / **revalidatePath** для **всех slug соседей** в той же группе (иначе у соседа в кэше старый `<head>` без новой ссылки). Это важный практический шаг.

## 5. Расширяемость языков и UX-баннер перевода

### 5.1. Локали и переключатель

- `locale` и ключи `alternates.languages` — **произвольные BCP-47**, не хардкод только `ru`/`en`: валидатор на API (allowlist или общий паттерн).
- В UI постоянный переключатель «языки» строится по соседям из группы (в шапке статьи или рядом с заголовком).

**Сделано (публичная статья `/article/[slug]`):** над телом статьи рендерится `ArticleTranslationLanguageNav` — ссылки на канонические URL опубликованных индексируемых соседей (`loadPublishedIndexableTranslationMembers`), текущая локаль помечена `aria-current`.

### 5.2. Всплывающий баннер «есть версия на вашем языке»

Идея: пользователь открыл **конкретный URL** (например EN), а предпочтения браузера — **RU**; в группе есть опубликованная **RU**-статья — показать **некликабельный до согласия** блок с кнопкой «Открыть на русском» (аналогично DE → предложить DE, если текущая страница не DE).

**Поведение:**

- **Без редиректа** — отдаётся тот же HTML, что и по ссылке; баннер только предлагает переход по явной ссылке на URL соседа.
- **Как узнать язык:** на сервере из заголовка **`Accept-Language`** (парсинг списка с `q`, сопоставление с префиксами `ru`, `ru-RU` → `ru`); на клиенте при гидрации можно уточнить `navigator.languages` — для баннера достаточно сервера, чтобы не мигало.
- **Логика выбора «подходящей» версии:** среди соседей группы найти статью, у которой `locale` **совпадает** с первым подходящим языком из `Accept-Language`, **и** этот язык **отличается** от `locale` текущей страницы. Если совпадений нет — баннер не показывать.
- **Закрытие:** кнопка «Не сейчас» / крестик; опционально **`localStorage`** или cookie по ключу `translation-banner-dismissed:{translationGroupId}` (или по текущему slug), чтобы не доставать повторно в рамках сессии или N дней.
- **Доступность:** регион с `role="region"` и `aria-label`, фокус на кнопке закрытия по желанию.

**Поисковики и боты:** они обычно **не выполняют** ваш клиентский баннер как «выбор пользователя»; главное — **не делать** редирект по `Accept-Language` на статьях. HTML по URL остаётся каноническим для этого URL; баннер — дополнительный UI. Не опирайтесь на blocklist User-Agent для «отключения баннера ботам» — не нужно: баннер не меняет индексируемый основной контент.

**Сделано:** `ArticleTranslationAcceptBanner` (client) — заголовок `Accept-Language` читается на сервере (`next/headers`), выбор соседа через `parseAcceptLanguageHeader` + `pickPreferredTranslationFromAcceptLanguage` (`~/lib/seo/acceptLanguageTranslationSuggest.ts`); отказ «Не сейчас» пишет в `localStorage` ключ `translation-banner-dismissed:{translationGroupId}` на **7 дней**; без редиректа.

**Вне scope:** `/private-article/...` — без баннера и без переключателя языков; там другой сценарий (доступ, noindex), публичный hreflang-кластер и предложение «версии по браузеру» относятся только к публичному `/article/...`.

### 5.3. Админка: удобное отображение связанных статей (переводы)

Одна запись в Mongo = одна языковая статья; в UI редактирования нужен блок **«Переводы»** / **«Языковые версии»**, данные — тот же хелпер соседей по `translationGroupId`, что и для SEO (плюс черновики, если админка их показывает).

**Рекомендуемый состав блока:**

| Элемент | Назначение |
|--------|------------|
| Таблица или список карточек | Колонки: **локаль** (бейдж `ru` / `en` / `de`), **заголовок** (из текущей ревизии или черновика), **slug**, **статус** (draft / published), **обновлён** |
| Текущая статья | Визуально выделена (фон, «вы здесь»), чтобы не путать с соседом |
| Действия | Ссылка **«Открыть в редакторе»** на каждую строку (переход на `/admin/.../articles/:id` или как у вас принято) |
| Пустые локали | Опционально: «Нет версии на DE» + кнопка **«Создать перевод (DE)»** — создаёт новый `Article` с тем же `translationGroupId`, `locale: de`, копирует по желанию заголовок-заготовку, редирект в редактор |
| Связка | Если `translationGroupId` ещё нет: **«Связать с существующей»** (по id) и/или **«Создать черновик перевода»** — UUID группы при необходимости создаётся на сервере; вручную в поле вставляют существующий id, без кнопки «перегенерировать», чтобы не ломать кластер по ошибке. |
| Отвязка | **«Отвязать эту статью»** — только текущая статья. **«Разорвать группу (все из списка)»** — один вызов `translation-unlink` по всем id из таблицы соседей: полный разбор кластера. |

**Компактный вариант (MVP):** одна строка-чипы под заголовком формы: `RU ✓` · `EN ✓` · `DE —` клик по чипу ведёт на редактирование соответствующей статьи; плюсик открывает мастер «новый язык».

**Список статей в админке:** колонка **«Языки»** — например `RU, EN` или иконка «🔗 3», hover / клик показывает тултип или переход к «главной» версии группы (например к той, у которой `locale === defaultLocale`).

**API (реализовано):**

- `GET /api/v1/article/translation-siblings/:articleId` — `{ translationGroupId, siblings }` (ADMIN/EDITOR).
- `POST /api/v1/article/translation-link` — тело `{ articleIds, translationGroupId? }`: общий `translationGroupId`, ревалидация и IndexNow по затронутым slug.
- `POST /api/v1/article/translation-unlink` — тело `{ articleIds }`: сброс `translationGroupId` / `locale` у выбранных id.
- `POST /api/v1/article/translation-publish-batch` — тело `{ articleIds }`: публикация черновиков группы (без замены обычного флоу публикации одной статьи).
- `POST /api/v1/article/translation-create` — тело `{ sourceArticleId, locale, slug?, sourceRevisionId? }`: новый `Article` + **черновая** `ArticleRevision` — **полная копия** указанной ревизии (`sourceRevisionId`, иначе `revisionId` статьи): контент, описание, title, `metadata` (SEO/OG/медиа); в SEO выставляются `language` = целевая локаль и `canonicalUrl` = `null` (каноник пересчитается под новый slug); группа и slug — как раньше.

Клиент: `ClientArticleApi.getTranslationSiblings`, `translationLink`, `translationUnlink`, `translationPublishBatch`, `translationCreate`.

### 5.4. Публикация: по одной, постепенно или группой — всё допустимо

Редактор решает сам: **сразу только RU**, **потом EN отдельной публикацией**, **потом ещё языки**, или **все в draft и разом** — валидация «все локали обязаны» **не требуется** и в продукте по умолчанию **не включается**.

**Обычная публикация (как сейчас):** каждая статья в группе живёт своим `status`; `PUT` на одну статью переводит в `PUBLISHED` независимо от соседей. SEO: после появления **второй** опубликованной версии в группе у **каждой** из них в `<head>` и sitemap появляются взаимные `alternates` только между **уже опубликованными** URL; одна опубликованная версия без пар — **нормально** (нет полноценного hreflang-кластера, но и ошибки нет).

**Удобство «выложить разом» (опциональная кнопка, не замена одиночной публикации):** в блоке переводов **«Опубликовать всю группу»** / **«Опубликовать выбранные»** — одна операция на бэкенде: выставить `PUBLISHED` выбранным id, **один** `notifySearchEngines` по всем затронутым URL, **одна** волна ревалидации по slug группы. Условия включения кнопки — только то, что вы считаете нужным в UI (например «все выбранные в draft»); **без** обязательных полей «готовности» на уровне API, если не хотите.

**Старые статьи:** ретроспективно присвоить одному `translationGroupId` двум (и более) существующим `Article` через **«Связать»**; или оставить без группы навсегда. **«Отвязать»** сбрасывает группу у выбранных документов.

**Отложенная публикация по расписанию** (`scheduledPublishAt` на группе) — **вне текущего scope** этого документа / репозитория (отдельный эпик, если понадобится).

**Итог:** поддерживаются **оба** пути — пошаговый выпуск и групповой; жёсткие политики вроде «нельзя опубликовать RU без EN» в базовом продукте **не закладываем** (максимум отдельный флаг организации в будущем, если когда-нибудь понадобится).
