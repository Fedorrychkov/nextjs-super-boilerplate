> **Сделано:** (1) `Typography` расширен — `tone: 'default' | 'muted'`, `asTag` до `h4..h6`, и **пустой дефолт** (без `variant` компонент не навязывает свои текстовые классы — className управляет полностью; добавлен проброс остальных HTML-атрибутов: `role`, `aria-*`, `id`, `onClick`, `dangerouslySetInnerHTML` и т.д.). (2) ESLint `no-restricted-syntax` (уровень `warn`) на `p`/`span`/`h1-6` + `input/textarea/select`, override для `src/components/ui/**`. (3) Все сырые `p`/`span`/`h1-6` в `src/**` (вне `ui/`) переведены на `Typography` (0 осталось). `typecheck` и `eslint` — чисто (0 ошибок).
> **Осталось:** поднять правило до `error`; витрина `/ui-kit`; раздел «Типографика» в `AGENTS.md`; ревью визуальных нюансов заголовков.

## Цель

Уйти от «сырых» текстовых тегов (`<p>`, `<span>`, `<h1>`–`<h6>`) в прикладном коде к единому компоненту `Typography`, который задаёт варианты, размеры и токены темы. Инлайновые/структурные теги форматирования (`<br>`, `<b>`, `<strong>`, `<i>`, `<em>`, `<ul>`/`<ol>`/`<li>`, `<a>` при необходимости) — **разрешены** и не ограничиваются. Плюс — **заложить принуждение** (ESLint + документация), чтобы разработчик и ИИ по умолчанию использовали `Typography` для текстовых блоков.

## Что уже есть

`src/components/ui/Typography/Typography.tsx` — единый компонент:

- Варианты (`variant`): `heading-1`, `heading-2`, `heading-3`, `Body/L|M|S|XS` × `Regular|Semibold` — каждому соответствует набор tailwind-классов (размер, вес, tracking, responsive).
- Полиморфизм тега (`asTag`): `'p' | 'span' | 'h1' | 'h2' | 'h3' | 'a' | 'label'`; при `href` автоматически рендерит `<a>` (`SafetyTag`).
- Токены темы: `text-foreground` по умолчанию, `text-secondary-600` для ссылок; `className` для доопределения.
- Пропсы ссылки/лейбла: `href`, `target`, `rel`, `htmlFor`.

Экспорт: `~/components/ui` → `Typography`.

## Пробелы `Typography`, которые надо закрыть до принуждения

1. **Нет `h4`–`h6` в `asTag`** и нет соответствующих вариантов. Сейчас `asTag` ограничен `h1|h2|h3`. Если в контенте/статьях встречаются более глубокие заголовки — расширить союз `asTag` и добавить варианты (или маппить `heading-3` на более глубокие уровни с меньшим размером). Для рендера **статей** (TipTap → HTML) заголовки идут через санитайзер, а не через `Typography` — это отдельный путь, его не трогаем (см. «Границы»).
2. **`span` внутри текста.** Много `<span>` — это инлайновые куски внутри абзацев (подсветка, счётчики, иконки+текст). Для них `Typography asTag='span'` работает, но заворачивать каждый мелкий инлайн — избыточно. Нужна чёткая граница: `Typography` для **самостоятельных текстовых блоков**; чисто презентационные инлайны (`<b>`, `<i>`, `<br>`, `<span>` только с классом внутри уже-типографированного блока) — разрешены.
3. **Доступность ссылок/лейблов.** `asTag='a'`/`'label'` уже есть; при миграции ссылок следить за `rel`/`target`/`htmlFor`.

## Enforcement (ESLint)

Аналогично полям — `no-restricted-syntax` в `eslint.config.mjs`, но с более аккуратной областью, т.к. текстовых тегов много и не все стоит запрещать жёстко.

Рекомендуемый стартовый набор — запретить **заголовки и абзацы** (однозначные кандидаты), `span` — на уровне `warn` (спорный, много презентационных):

```js
'no-restricted-syntax': [
  'warn', // старт как warn; после миграции — error
  {
    selector: "JSXOpeningElement[name.name=/^(h1|h2|h3|h4|h5|h6)$/]",
    message: 'Не используй сырые заголовки. Возьми <Typography asTag="h1|h2|h3" variant="heading-*"> из ~/components/ui.',
  },
  {
    selector: "JSXOpeningElement[name.name='p']",
    message: 'Не используй сырой <p>. Возьми <Typography> из ~/components/ui.',
  },
  {
    selector: "JSXOpeningElement[name.name='span']",
    message: 'Для самостоятельного текста используй <Typography asTag="span">. Чистые презентационные инлайны (внутри уже типографированного блока) допустимы — при необходимости // eslint-disable-next-line с обоснованием.',
  },
],
```

**Разрешены явно** (не в списке): `br`, `b`, `strong`, `i`, `em`, `ul`, `ol`, `li`, `small`, `code` и т.п. — их не ограничиваем.

**Override — снять правило для примитивного слоя** (там сырые теги легитимны — сам `Typography`, `ui/*`):

```js
{
  files: ['src/components/ui/**/*.{ts,tsx}'],
  rules: { 'no-restricted-syntax': 'off' },
},
```

> Если в `docs/develop/field-components.ru.md` уже добавлен `no-restricted-syntax` для `input/textarea/select`, **объединить оба набора в один массив** правила (ESLint позволяет только один `no-restricted-syntax` на конфиг-блок) — селекторы полей и текста в одном списке, один общий override для `src/components/ui/**`.

## Границы (что НЕ трогаем)

- **Рендер статей.** Публичный HTML статей строится из TipTap JSON → статический рендер → DOMPurify (`src/lib/sanitize/articleHtml.ts`). Там `p/h1..h6/span` — это выход санитайзера, а не JSX-код разработчика. Правило действует на `.tsx`-исходники, этот путь не затрагивает.
- **Презентационные инлайны** внутри уже типографированного текста — `b`, `i`, `br`, `span` с классом. Не заворачиваем в `Typography`.
- **Сторонние/примитивные компоненты** в `src/components/ui/**` — исключены override-ом.

## Открытые вопросы

- `span` в правиле — оставить `warn` навсегда (мягкая рекомендация) или довести до `error` после разбора? (Рекомендация: `warn`, т.к. презентационных инлайнов много и жёсткий запрет создаст шум.)
- Расширять ли `asTag` до `h4..h6` сейчас или по факту появления таких заголовков? (Рекомендация: по факту.)
- Нужен ли отдельный вариант для «caption/muted» текста (частый кейс `text-muted-foreground text-xs`), чтобы не тянуть `className` каждый раз? (Кандидат в новые `variant`.)
